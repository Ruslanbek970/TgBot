# Как реализован локальный диск

Этот проект не использует внешний облачный диск вроде Google Drive, Dropbox или Яндекс Диска. Под "диском" здесь понимается self-hosted хранилище документов: сами файлы лежат на локальной файловой системе сервера, а информация о них хранится в PostgreSQL или, если база недоступна, в локальном JSON-индексе.

Основная реализация находится в `storage/store.py`.

## Общая идея

Хранилище разделено на две части:

1. Физическое хранение файлов.
2. Метаданные для поиска, списка файлов и скачивания.

Файлы сохраняются в папку:

```text
storage/secure_files/
```

Метаданные сохраняются в PostgreSQL:

```text
storage_companies
storage_documents
storage_users
storage_access_logs
```

Если PostgreSQL недоступен, используется fallback:

```text
storage/index.json
```

Также поддерживается старый формат хранения:

```text
storage/documents/<Компания>/<файлы>
```

Он нужен для совместимости с ранней файловой заглушкой и демо-документами.

## Почему файлы лежат не под оригинальными именами

Когда пользователь загружает документ, файл не кладется напрямую как:

```text
storage/secure_files/договор.pdf
```

Вместо этого создается UUID:

```text
697fb3f2cc5e43958f1af82e44d68155
```

И файл сохраняется по пути вида:

```text
storage/secure_files/69/7f/697fb3f2cc5e43958f1af82e44d68155
```

Первые две пары символов UUID используются как подпапки. Это сделано, чтобы не складывать тысячи файлов в одну директорию. Такая структура лучше масштабируется и быстрее обслуживается файловой системой.

Оригинальное имя файла сохраняется отдельно в метаданных:

```text
original_name = "договор.pdf"
secure_path = "storage/secure_files/69/7f/697fb3f2cc5e43958f1af82e44d68155"
```

Поэтому пользователь видит нормальное имя файла, а на диске файл хранится под техническим безопасным идентификатором.

## Основные папки

### `storage/secure_files/`

Основная папка для новых загруженных файлов.

Файл внутри этой папки:

- имеет UUID вместо оригинального имени;
- разложен по подпапкам по первым символам UUID;
- связан с оригинальным названием через PostgreSQL или `index.json`.

### `storage/documents/`

Legacy-хранилище.

Структура:

```text
storage/documents/
  Тексол Транс/
    протокол.txt
    сертификат.txt
```

Этот режим проще: папка означает компанию, файлы внутри папки считаются документами этой компании.

Код все еще умеет искать и отдавать документы из этой папки, но новые загрузки в нормальном режиме идут в `storage/secure_files/`.

### `storage/index.json`

Fallback-индекс, если PostgreSQL недоступен.

Примерная структура:

```json
{
  "companies": {
    "common": {
      "name": "Common"
    }
  },
  "documents": [
    {
      "id": "697fb3f2cc5e43958f1af82e44d68155",
      "company": "Common",
      "original_name": "report.pdf",
      "secure_path": "storage/secure_files/69/7f/697fb3f2cc5e43958f1af82e44d68155",
      "size": 12345
    }
  ]
}
```

## PostgreSQL-схема

Схема описана в `storage/schema.py`.

### `storage_companies`

Хранит компании.

Основные поля:

```text
id
name
created_at
```

### `storage_documents`

Хранит документы и связь с физическим файлом.

Основные поля:

```text
id
company_id
original_name
secure_path
file_size
min_role
search_text
search_vector
created_at
```

`secure_path` указывает на реальный файл в `storage/secure_files/`.

`original_name` хранит имя, которое видел пользователь.

`search_vector` используется для поиска через PostgreSQL full-text search.

### `storage_users`

Заготовка под пользователей и роли.

Основные поля:

```text
telegram_id
username
role
is_active
created_at
```

Сейчас в коде роли почти не применяются, но таблица уже подготовлена.

### `storage_access_logs`

Заготовка под журнал доступа.

Основные поля:

```text
id
telegram_id
document_id
action_type
allowed
created_at
```

Функция `log_access()` уже есть, но основная логика бота пока почти не использует аудит.

## Как файл загружается

Основной поток находится в `bot/main.py`, обработчик `on_document()`.

Последовательность:

1. Пользователь отправляет документ, фото или ZIP-архив в Telegram.
2. Бот получает файл через Telegram Bot API.
3. Файл временно сохраняется в системную temp-папку.
4. Если это ZIP, архив проверяется и распаковывается.
5. Если в подписи указан формат конвертации, файл отправляется в конвертер.
6. Если файл надо сохранить, вызывается:

```python
save_document(company, src_path, file_name)
```

7. `save_document()` создает UUID.
8. Файл копируется в `storage/secure_files/<xx>/<yy>/<uuid>`.
9. Метаданные записываются в PostgreSQL.
10. Если PostgreSQL недоступен, метаданные записываются в `storage/index.json`.
11. Временный файл удаляется.

По умолчанию файлы сохраняются в компанию:

```text
Common
```

Если пользователь заранее написал:

```text
/add_file <компания>
```

то следующий файл сохранится в указанную компанию.

Также компания может быть указана в подписи к файлу:

```text
save to <компания>
сохранить в <компания>
```

## Как файл скачивается

Для скачивания используется команда:

```text
/download <компания> <файл>
```

Поток:

1. Бот парсит компанию и имя файла.
2. Вызывает:

```python
get_document(company, filename)
```

3. `get_document()` ищет документ в PostgreSQL.
4. Если в БД не найдено или БД недоступна, проверяется JSON/fallback-хранилище.
5. Если найден физический файл, возвращается пара:

```python
(secure_path, original_name)
```

6. Бот открывает файл по `secure_path`.
7. Пользователю файл отправляется с видимым именем `original_name`.

То есть физически файл может называться UUID, но в Telegram пользователь получает файл с нормальным оригинальным названием.

## Как работает поиск

Основная функция:

```python
find_documents(query) -> list[str]
```

Она возвращает список путей к найденным файлам.

Поиск идет в несколько этапов:

1. Если PostgreSQL доступен, выполняется поиск по:
   - названию компании;
   - оригинальному имени файла;
   - `search_vector`.
2. Дополнительно используется поиск по отдельным словам запроса.
3. Затем подключается fallback-поиск по JSON-индексу.
4. Затем проверяются legacy-файлы в `storage/documents/`.

Для компаний используется fuzzy-поиск из `storage/fuzzy_search.py`. Это помогает находить компанию даже при неточном запросе.

Например запрос:

```text
покажи документы по Тексол
```

может найти компанию:

```text
Тексол Транс
```

## Как работает список компаний

Функция:

```python
list_companies()
```

Собирает компании из нескольких источников:

1. PostgreSQL `storage_companies`.
2. JSON-индекс `storage/index.json`.
3. Папки в `storage/documents/`.

Результат объединяется и сортируется.

## Как работает список файлов

Функция:

```python
list_files(company)
```

Сначала имя компании уточняется через `_resolve_company_name()`. Это позволяет использовать неточное название.

Затем список файлов собирается из:

1. PostgreSQL `storage_documents`.
2. JSON/fallback-хранилища.
3. Legacy-папки `storage/documents/<Компания>/`.

Пользователю возвращаются оригинальные имена файлов, а не UUID.

## Как работает удаление файла

Функция:

```python
delete_file(company, filename)
```

Удаляет:

1. Физический файл из `storage/secure_files/`.
2. Запись из PostgreSQL.
3. Запись из JSON-индекса, если используется fallback.
4. Legacy-файл из `storage/documents/<Компания>/`, если он там есть.

После удаления файла код также пытается удалить пустые технические подпапки внутри `secure_files`.

## Как работает удаление компании

Функция:

```python
delete_company(name)
```

Удаляет:

1. Компанию из PostgreSQL.
2. Все связанные документы компании.
3. Физические файлы этих документов из `secure_files`.
4. Компанию из JSON-индекса.
5. Legacy-папку `storage/documents/<Компания>/`, если она есть.

В PostgreSQL связь настроена через:

```sql
REFERENCES storage_companies(id) ON DELETE CASCADE
```

Это значит, что при удалении компании записи документов в БД удаляются каскадно. Но физические файлы на диске удаляются отдельно кодом.

## Docker и постоянное хранение

В `docker-compose.yml` примонтированы две папки:

```yaml
volumes:
  - ./storage/documents:/app/storage/documents
  - ./storage/secure_files:/app/storage/secure_files
```

Это значит:

- файлы хранятся на машине хоста;
- пересборка Docker-образа не удаляет документы;
- контейнер видит эти папки внутри `/app/storage/`.

PostgreSQL хранит данные в отдельном volume:

```yaml
postgres_data:/var/lib/postgresql/data
```

Это защищает базу от потери данных при перезапуске контейнера.

## Публичный API storage-модуля

Бот работает с хранилищем через функции из `storage/__init__.py`:

```python
find_documents(query)
list_companies()
save_document(company, temp_file_path, file_name)
create_company(name)
delete_company(name)
list_files(company)
delete_file(company, filename)
get_document(company, filename)
log_access(telegram_id, document_id, action_type, allowed)
```

Бот не должен знать, где именно лежит файл и используется ли PostgreSQL или JSON. Это скрыто внутри `storage/store.py`.

## Важные ограничения текущей реализации

1. Файлы не шифруются на диске.

   Они скрыты под UUID, но это не криптографическая защита. Если нужен реальный secure storage, нужно добавить шифрование содержимого файлов.

2. Роли доступа подготовлены, но почти не применяются.

   В БД есть `min_role`, `storage_users` и `storage_access_logs`, но полноценной проверки прав в обработчиках бота пока нет.

3. JSON fallback удобен для отказоустойчивости, но не заменяет полноценную БД.

   При параллельных записях JSON может стать слабым местом. Для production лучше полагаться на PostgreSQL.

4. Legacy-папка `storage/documents/` все еще участвует в поиске.

   Это удобно для демо и совместимости, но может создавать дубли, если одни и те же документы есть и там, и в `secure_files`.

5. Физические файлы и БД должны быть консистентны.

   Если вручную удалить файл из `secure_files`, запись в БД останется, но код не отдаст документ, потому что проверяет `os.path.isfile(path)`.

## Краткая схема

```text
Telegram user
    |
    v
bot/main.py
    |
    v
storage.save_document()
    |
    +--> storage/secure_files/<uuid path>
    |
    +--> PostgreSQL storage_documents
             |
             +--> original_name
             +--> secure_path
             +--> company_id
             +--> search_vector

Если PostgreSQL недоступен:
    |
    +--> storage/index.json
```

## Итог

Текущий "диск" - это локальное файловое хранилище с UUID-путями и индексом в PostgreSQL. База знает, какой файл как называется, к какой компании относится и где лежит на диске. Сам файл хранится локально, поэтому документы не уходят во внешние сервисы.
